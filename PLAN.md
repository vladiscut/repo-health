# Repo Health Score — план работ

Документ заменяет старый `repo_health_score_plan.md`. База — **ТЗ** (`8. Yandex Cloud.pdf`). Созвон уточняет API (AppSec, Discover, PAT, 100 rps), но не отменяет обязательную часть ТЗ.

Сдача: репозиторий на SourceCraft + команда/ссылка, как поднять сервис. Нейрокод и бойлерплейт — минус. Креатив в методике и использовании API — плюс.

## 2. Архитектура

```
                    ┌──────────── /  public ────────────┐
Discover GET /repos │  рейтинг, карточка, без логина    │
        24h beat    │  очередь analysis.scheduled       │
                    └────────────┬──────────────────────┘
                                 │ один Django, общая БД
                    scoring, collectors, rate limiter
                                 │
                    ┌────────────┴──────────────────────┐
Я ID + PAT          │  /me/  кабинет, тренд, отчёт      │
AppSec + CI/CD      │  очередь analysis.user            │
                    └───────────────────────────────────┘
```

Не два сервиса и не два деплоя. Один `web-repo-health`, префиксы URL и две Celery-очереди. `SERVICE_ROLE` не нужен, пока не решим скейлить `/me/` отдельно.

Один scan-job на репозиторий, не Celery `chord` из шести HTTP-задач: иначе упрёмся в 100 rps. Внутри job — последовательный сбор с общим лимитером; параллелить только CPU-скоринг.

Инфраструктура MVP: текущий `docker-compose.yml`. Beat вынести в отдельный сервис (сейчас `-B` на worker — допустимо для демо, в README это описать). Прод-nginx не делаем, пока нет стенда.

## 3. Методика Score v1

Версия формулы хранится в `Scan.raw["scoring_version"]` (поле модели можно добавить позже). Сбор метрик и расчёт **раздельны**: `MetricSample` → чистая функция → `HealthScore` + `Finding`.

### 3.1. Итог

Итог = взвешенная сумма **доступных** категорий, веса перенормируются к 1.0.

Итог = взвешенная сумма **доступных** категорий, веса перенормируются к 1.0.

Базовые веса — **таблица-ориентир из ТЗ §3.2**. ТЗ прямо говорит: веса необязательны, команда может свои. Свои веса предлагаем только если упрёмся в методику; до этого не плодим седьмую категорию.

| Категория | Вес | Источник |
|---|---|---|
| Security | 20% | ТЗ |
| Code health | 20% | ТЗ |
| Активность проекта | 15% | ТЗ; внутри — коммиты, релизы, **лайки (лог)** |
| Документация | 15% | ТЗ |
| CI/CD | 15% | ТЗ; в public недоступна |
| Issues | 15% | ТЗ |
| Итого | 100% | |

Лайки в таблице рейтинга обязательны (ТЗ §4: колонка и сортировка). В Score они не отдельная категория: иначе рейтинг здоровья превращается в рейтинг популярности, а ТЗ это запрещает. Внутри Activity лайки ~25% категории (~4% итога), логарифм до ~200. Contributors — тоже Activity, как в ТЗ.

**Публичный рейтинг без Security и CI/CD.** Недоступны 20% + 15%. Итог по оставшимся 65%, перенормировка к 100%:

| Категория | Базовый вес | Доля в public |
|---|---|---|
| Code health | 20% | ~31% |
| Docs | 15% | ~23% |
| Activity (в т.ч. лайки) | 15% | ~23% |
| Issues | 15% | ~23% |

На карточке public явно: «CI/CD и Security недоступны без доступа к репозиторию». В `/me/` обе категории включаются.

Если тип репо `data` / `empty` → **total = 0**, категории можно посчитать для отчёта, но в рейтинге сортировка отдельно и бейдж «не код».

«Нет данных» по категории: `HealthScore.total = null`. Не путать с 0.

### 3.2. Метрики v1

**Docs** — дерево файлов, не «всегда True».

- README есть / нет (нет = плохо).
- Есть разделы установки/запуска (эвристика заголовков) — плюс.
- LICENSE, CONTRIBUTING — плюс.

**CI/CD** — только personal, как AppSec.

- Public: категорию не собираем, `is_available=false`, причина «нет доступа к CI чужого репо». Не 0 и не «нет пайплайна».
- Personal: смотрим `.sourcecraft/ci.yaml` (или аналог) и `cicd/runs`. Нет конфига — факт, низкий балл, не null. Есть конфиг и runs: доля success, ссылка на последний красный.
- Начинать с наличия CI — про личный контур, не про публичный рейтинг.

**Security** — только personal.

- Public: не дергаем AppSec, `is_available=false`.
- Personal: `GET /v1/scans/latest` + findings + defect-groups.
- Скан FINISHED, находок 0 → высокий балл.
- Скана не было при валидном PAT → тоже «нет данных», пока не запущен AppSec; если запущен и чистый — не null.
- SCA: прямые и транзитивные входят в оценку. Секреты и SAST — отдельные счётчики.

**Activity**

- Дата последнего коммита / дерева HEAD, частота, релизы, PR, contributors — как в ТЗ.
- Лайки / `rating.reaction_counts`: ~25% категории, логарифм `min(100, 100 * log10(1 + likes) / log10(1 + 200))`. Ноль лайков — факт 0, не «нет данных».
- В таблице рейтинга лайки отдельной колонкой и отдельной сортировкой (ТЗ §4). Главная сортировка — наш Score.

**Issues**

- Открытые / зависшие, если API отдал список. 0 открытых при доступном API — хорошо. 404 issues → нет данных.

**Code health v1 (без клона, по API)**

- TODO/FIXME по дереву/поиску, если получится дёшево.
- Манифест vs lock: `requirements.txt` / `pyproject` / `package.json` vs lockfile, расхождение имён/версий.
- Пустой репозиторий, одни csv/json без исходников → тип `data`.

**Code health v2 (клон, плюс)**

- Мёртвые импорты, подозрительные нейролупы (одинаковые блоки / сгенерированные файлы), полный SCA по lockfile.
- Опционально: ИИ «README описывает то, чего нет в коде» — отдельный finding, Score не должен зависеть от LLM (иначе недетерминизм). ИИ только рекомендация.

### 3.3. Антинакрутка нашего сервиса

Речь не про детект фейковых лайков на SourceCraft — заказчик сказал «никак». Речь про то, что **наш** рейтинг нельзя взломать.

- Метрики только из нашего пайплайна (SourceCraft/AppSec). Нет API «загрузить score / raw».
- Публичный rescan — beat или management-команда. Открытый POST без лимита и без роли — нельзя.
- Personal PAT-скан не пишет и не обновляет строку публичного рейтинга.
- Нельзя подставить чужой `org/repo` в personal и этим попасть в public top.
- Пустой README / пустой `ci.yaml` не дают максимум категории.
- Data-only / empty = 0 при любом числе лайков.
- Лайки с логарифмическим потолком: массовая накрутка реакций почти не двигает итог после ~200.
- Throttle на personal rescan и на добавление репо.

## 4. Интеграции

### 4.1. SourceCraft (`integrations/sourcecraft.py`)

Доделать, не писать второй клиент:

- Discover: уже `GET /repos`. Обход с `sort_by=created_at`, курсор, уважение «не snapshot».
- Хранить `sourcecraft_id` (id/uuid из API) — он нужен AppSec как `gitRepo`.
- `logo_url` и описание — необязательные поля модели (`blank=True`).
- Коммиты: не подменять `trees` без пометки; для activity брать то, что API реально даёт (дерево HEAD + дата `last_updated` / commit, если появится).
- Типизированные ошибки: 404, 401/403, 429, 5xx — уже задуманы в старом плане, в коде ещё нет.
- Клиент принимает `access_token` аргументом (сейчас берёт только `settings.SOURCECRAFT_API_TOKEN`) — иначе personal не заработает.

### 4.2. AppSec (`integrations/appsec.py`) — новый

База `https://appsec.sourcecraft.tech`. Методы MVP:

- `GET /v1/scans/latest?gitRepo=`
- `GET /v1/findings?gitRepo=`
- `GET /v1/defect-groups` (SCA/SAST/SECRETS, severity)
- при наличии — SBOM/зависимости, флаг direct vs transitive

Тот же rate limiter, Bearer PAT.

### 4.3. Rate limit

Один Redis-ключ `ratelimit:upstream` на 100 запросы/сек на все воркеры. Перед каждым HTTP. 429 — уважать Retry-After + наш bucket.

## 5. Фазы и задачи

Каждая фаза заканчивается чем-то, что можно показать. Не начинать фазу 3, пока 0–2 не зелёные: жюри первым делом поднимает сервис.

### Фаза 0 — витрина живая (1–2 дня)

Цель: `docker compose up --build` → список с числами, карточка с 6 категориями, README с одной командой.

0.1. Собрать итоговый Score в views (взвешенная сумма) и починить `repo_list.html` / `repo_detail.html` / историю. «Нет данных» серым, не как низкий балл.  
0.2. `latest_scan()` — последний `success` или `partial`, не `running`.  
0.3. README: compose, порт, что открыть, как выглядит демо, `celery -A core`. Убрать `config`.  
0.4. `seed_demo` вызывает `score_from_raw`, не копирует формулу.  
0.5. Admin: убрать поиск по несуществующему `name`.  
0.6. `logo_url` / `url` не обязательны.

**Готово когда:** без токенов, только seed, UI не врёт.

### Фаза 1 — публичный контур с API

1.1. Redis rate limiter 100 rps, тесты на мок-часах.  
1.2. Management-команда `discover_public_repos` + Celery beat 24h. Upsert по `sourcecraft_id`.  
1.3. Если Discover/Get сказал не public или 404 — `visibility` обновить, **исключить из рейтинга**.  
1.4. Public-скан: дерево/README, issues, releases, contributors, лайки. **Не** `cicd/runs` и не AppSec. Фейк `_collect_raw` удалить.  
1.5. Очередь `analysis.scheduled`. Идемпотентность: не плодить второй `running` по тому же репо.  
1.6. Публичный рейтинг по ТЗ §4: место, Score, лайки, язык, активность. Сортировки: Score (главная), лайки, дата. Фильтр по языку.

**Готово когда:** на токене команды в списке реальные public, не три seed-репо (seed выключить в prod-команде).

### Фаза 2 — движок Score + тесты (обязательно по созвону)

2.1. `health/scoring/config.py`: веса, пороги, `SCORING_VERSION`.  
2.2. Правило «нет данных» / перенормировка / data-only=0 / empty=0.  
2.3. Классификатор типа: `empty`, `data`, `library`, `backend`, `frontend`, `unknown` (эвристика по дереву и языку).  
2.4. Findings rule-based, как сейчас модель `Finding`.  
2.5. Тесты pytest:

- каждая категория: один сигнал вверх и вниз;
- public-скан: CI/CD и Security = null, итог по 5 категориям;
- personal без CI-конфига → CI низкий, `is_available=true`;
- нет README → Docs низкий в обоих контурах;
- AppSec clean + commit (personal) → Security не null;
- data-only → 0 даже при большом `likes`;
- рост likes 0→20 двигает Activity заметно, 500→5000 — почти нет;
- likes не меняют Security / CI / Docs;
- нельзя через API записать готовый total;
- одинаковый вход → одинаковый выход.

2.6. SourceCraft CI: `pytest` на push (наличие CI у *нашего* репо — и сигнал жюри, и самооценка).

**Готово когда:** `pytest` зелёный без сети.

### Фаза 3 — Я ID, кабинет `/me/`, отчёт

3.1. OAuth Я ID (ТЗ §5): кнопка входа, User по `ya_id`.  
3.2. После логина — форма PAT, шифрование, привязка к User.  
3.3. Список своих репо: PAT + указанные `org/repo` (в REST нет `/me/repos`).  
3.4. Дашборд: мои репо, Score, график истории Scan.  
3.5. Rescan → `analysis.user`. Throttle.  
3.6. Изоляция: скан из `/me/` не обновляет публичный рейтинг.  
3.7. В этом job: CI/CD под PAT.  
3.8. Выгрузка отчёта **Markdown** (обязательно). PDF — если останется время.

**Готово когда:** два URL, на одном рейтинг, на другом только «мои» после PAT.

### Фаза 4 — AppSec и SCA

4.1. `AppSecClient`, gitRepo = uuid/id.  
4.2. Findings по engine SCA/SAST/SECRETS, severity, статус.  
4.3. Транзитивные зависимости входят в Security/Code health (явно в объяснении: direct / transitive).  
4.4. Публичный контур AppSec не вызывает. Только personal.  
4.5. Тест: clean scan ≠ no data; transitive CVE снижает балл.

**Готово когда:** на своём репо карточка Security из AppSec, не из имени workflow.

### Фаза 5 — плюсы (креатив, не блокируют питч)

5.1. Клон по `clone_url` + PAT на воркере, tmp, удалить после скана.  
5.2. Мёртвый код, расхождение lockfile, нейролуп-эвристика.  
5.3. ИИ-рекомендация «документация ↔ код», Score без LLM.  
5.4. PDF-отчёт (Markdown уже в фазе 3).  
5.5. Сравнение рейтинга внутри типа (библиотеки отдельно от сайтов).
